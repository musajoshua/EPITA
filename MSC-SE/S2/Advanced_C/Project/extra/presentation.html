Project Scope

Goal: Build a functional Unix shell from scratch in C99


Why a shell?

  • Touches nearly every core C concept: memory, pointers, strings, arrays
  • Deep dive into POSIX system calls: fork, exec, pipe, dup2
  • Process management, signals, file descriptors
  • Terminal I/O at the lowest level

~900 lines of C across 9 source files. No external libraries — only the C standard library and POSIX.

1 The REPL Skeleton

The shell is an infinite loop:

while (1) {
    print "jsh $ "
    line = read input
    if EOF → break
    if empty → skip
    tokens = tokenize(line)
    run_command_line(tokens)
    free everything
}
  • Ctrl+D → EOF → exits the loop
  • Empty lines are skipped, no crash
  • Every iteration: allocate, use, free — no leaks

2 Tokenizer

Splits a string into an array of words:

"ls -la /tmp"  →  ["ls", "-la", "/tmp", NULL]

  • Walks the string character by character
  • Skips whitespace, extracts each word
  • Each token gets its own malloc'd copy
  • Array grows dynamically (doubles when full)
  • NULL-terminated — ready for execvp

3 Command Execution

Three system calls to run any program:

fork()
Creates an exact copy of the shell process.
Returns twice: 0 in child, child's PID in parent.
execvp()
Replaces the child's code with the actual command.
The child becomes /bin/ls (or whatever).
waitpid()
Parent blocks until the child finishes.
Then prints the prompt again. 
JSH (parent)
    |
  fork()
    |          \
 parent      child
    |          |
 waitpid   execvp("ls")
 (waits)       |
    |       child is now
    |       /bin/ls
    |          |
    |       ls exits
    |          |
 waitpid   <-- done
 returns
    |
 prompt again

4 Built-ins & Signals

Why built-ins?

cd must run in the parent process.

If cd ran in a forked child, the child would change its directory — then exit. The parent's directory would never change.


CommandWhat it does
cd [dir]chdir() in parent
pwdgetcwd() + print
exitexit(0)

Signal handling

Parent: signal(SIGINT, SIG_IGN)
Ignores Ctrl+C so the shell itself doesn't die.
Child: signal(SIGINT, SIG_DFL)
Restores default behavior before execvp, so Ctrl+C kills running commands.

5 I/O Redirection

File descriptors are like TV channels:

fdDefaultWhat it does
0 (stdin)KeyboardWhere input comes from
1 (stdout)ScreenWhere output goes
2 (stderr)ScreenWhere errors go

open() opens a file → returns fd 3

dup2(3, 1) retunes fd 1
stdout now points to the file 
echo hello > out.txt

Before: fd 1 → screen
After:  fd 1 → out.txt

echo writes to fd 1 as usual
but it goes to the file now

Runs in the child only — parent's fds stay untouched.

6 Pipes

pipe(fd) creates a one-way data channel between two processes:

pipe(fd) → fd[0] = read end, fd[1] = write end

ls | grep .c

1. Create pipe
2. Fork ls  → redirect stdout to pipe write end → execvp
3. Fork grep → redirect stdin to pipe read end  → execvp
4. Parent closes both pipe ends
5. Parent waits for both children

  • ls writes to stdout → goes into the pipe
  • grep reads from stdin → reads from the pipe
  • Neither knows about the other. The pipe connects them through the kernel.
  • Must close unused pipe ends — otherwise the reader hangs forever waiting for EOF

6 Multi-Pipe Chaining

For ls | grep .c | wc -l, we chain pipes using prev_fd:

Iteration 1: pipe() → fork ls child → save read end as prev_fd
Iteration 2: pipe() → fork grep child
               stdin  ← prev_fd (reads ls output)
               stdout → new pipe write end
             → save new read end as prev_fd
Iteration 3: no new pipe (last command)
             → fork wc child
               stdin ← prev_fd (reads grep output)
             → execvp wc

Each middle command reads from the previous pipe and writes to a new one.

The parent tracks which pipe read-end to pass to the next iteration.

7 Operators & Glob Expansion

Operators

OpRule
;Always run next
&&Run next only if previous succeeded (exit 0)
||Run next only if previous failed (exit ≠ 0)

gcc main.c && ./a.out
  → only runs a.out if gcc succeeded

gcc main.c || echo FAIL
  → only echoes if gcc failed

Glob expansion

The shell expands wildcards, not the command:

ls *.c
  → ls main.c pipes.c executor.c ...
  • strchr(token, '*') — does it have a wildcard?
  • glob() — find matching filenames
  • Splice matches into the token array
  • No matches? Keep original token as-is

8 Raw-Mode Line Editor

Problem: getline() uses "cooked mode" — no control over arrow keys or history.

Solution: Switch to raw mode using termios:


Disable ECHO
Characters are not auto-printed.
We manually echo each one with write().
Disable ICANON
Input delivered one character at a time
instead of waiting for Enter.
Character loop:
Printable → append + echo
Enter → save to history, return
Backspace → erase last char
Arrow keys → navigate history
Ctrl+D → return NULL (EOF)
History:
Static array of up to 100 entries.
Up/down arrows cycle through them.
Line is redrawn on each navigation.

Difficulties & Design Choices

  • Pipe fd leaks: Forgetting to close unused pipe ends caused child processes to hang forever waiting for EOF. Every fd must be closed in every process that doesn't use it.

  • Redirections in the child only: Redirections run after fork() but before execvp(), so the parent's file descriptors stay untouched.

  • cd must be a builtin: Running cd in a forked child changes the child's directory — which is useless because the child exits immediately.

  • Raw mode terminal: Had to handle every character manually — including escape sequences for arrow keys (3-byte sequences).

  • Memory discipline: Every malloc has a matching free. Token arrays, line buffers, glob results — all freed after use.
